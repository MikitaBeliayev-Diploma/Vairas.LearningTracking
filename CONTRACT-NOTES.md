# Learning Tracking implementation amendments

Baseline D-042 remains adopted domain design. Frozen `api/source`, `database/schema.dbml` and initial SQL retain the supplied source material. The generated `api/learning-tracking.openapi.json` / `.yaml` describe the implemented HTTP surface; implementation migrations and this document describe additions without retroactively changing adoption history.

- Retain the 31 canonical domain tables and exact composite FK/CHECK rules. Add version-owned `lesson_planning_policy` and technical `learning_operation`, `outbox_message`, `inbox_message`, `enrollment_source_state`, `policy_attestation`, `school_source_state`. No credit ledger, JSONB checklist, document-file tables or programme transfer is introduced. JSON text is limited to command outcomes and integration transport bodies.
- Use EF migrations for canonical initial/null-safe SQL, reliability/planning, then monotonic School revision tracking. SQL remains authoritative for deferred relationships. The initial generated designer uses the final scalar mapping set; install all migrations before serving requests. No startup migrations or automatic destructive downgrade.
- Current user requests resolve Auth IdentityId/session and UM UserId/profile IDs independently. Workloads use distinct audiences, signed scopes and local allowlists. Public and workload tokens are not interchangeable. Incoming workload clients and secrets require external provisioning.
- Add programme draft/version/publication APIs, exact source verification, assessment result corrections/history, normalized evidence preparation/revalidation and manual reporting declarations. Require explicit `schoolId` and a nonempty UUID idempotency key for user writes except deterministic source verification. First creates return 201 with Location; replay returns 200 with the saved original outcome after fresh authority checks. Historical result history supplies no CAS token for signing a newer version.
- Practical aggregate `revision` is the current CAS token; `factVersion` identifies immutable facts. Confirming one role advances aggregate revision, and the other participant must use the new revision while confirming the same fact version. No administrator signatures. A dispute closes that fact version permanently. `creditEligible` and `RevalidationRequired` distinguish a source/policy hold from historical participant confirmations.
- Theory versions permit one narrow audited `confirmedBy/confirmedAt` transition, enforced by a SQL trigger and column grants. Remaining material fields stay immutable. Confirmation compares exact current revision, fact version, source and the full retained historical roster. Group-member corrections create a new fact version. A learner never reads the full group roster through the journal API.
- `Progress.percent` is nullable when the configured denominator is zero. An enrollment without a pinned programme reports `AwaitingProgramme`, with null deficits and percentage. It is capped at 100%; deficits remain separate. Legacy `ConfirmedPracticalRecords.records[].actualMinutes` means eligible teaching minutes for compatibility, not Scheduling's physical interval.
- Scheduling owns physical status, actual bounds and lesson revision. Events are change hints; source facts are verified via its current `training-source` leaf. Stale revisions are classified before old body validation; equal-revision disagreement holds reconciliation. Owner unavailability retains immutable history, withdraws current eligibility and terminally invalidates affected approvals. Restore of a source cannot revive those decisions.
- A performed final assessment changes subsequent dependency state without retroactively invalidating its own lawful approval merely because its result was added. Corrections and unknown historical defects hold affected results for authorized review; prospective changes after `assessedAt` retain historical eligibility. A terminally invalidated approval cannot authorize a new attempt.
- School authority includes the exact current/prospective programme association, membership and Assessor grant. `evidenceRevalidation=true` is a read-only workload leaf used by completion coordination; it does not admit new Learning commands while School changes are pending. Consecutive verified School revisions may carry prospective effective time; unknown/skipped revisions require a historical hold. Late events at an already observed School revision cannot invalidate a newer decision.
- School Completed retains the exact `EvidenceSnapshotId`, `DependencyRevision` and verification time in its existing status history. A current proof is checked before coordination and again before local apply. The existing group-removal prerequisite and terminal-history timestamps remain enforced. The retained evidence link is logical, never a cross-service SQL FK.
- Implement expected POST `internal/v1/scheduling/planning-inputs`, `assessment-evidence`, `programme-applicability`. Applicability validates a prospective group before association, preventing School↔Learning initialization recursion. Planning uses configured session policy, eligible completed facts and separately labelled current allocations. It never gives planned time learning credit. Group members with differing residual curriculum need an explicit split.
- Add Scheduling read-only `internal/v1/learning/allocations` and `assessment-appointments/{id}`. They expose only exact scoped owner data to `scheduling.source.read`; reservation and Vehicle checks remain Scheduling responsibilities.
- Implement Azure Service Bus per producer-family topic, MessageId=eventId, Subject=eventType and common application headers. Business change/audit/Outbox or source change/Inbox commit locally together. Claims use leases, bounded backoff and idempotent recovery. Poison messages are dead-lettered with safe diagnostics. Reconciliation polls owner leaves after transport outages; it does not infer credit from receipt of an event.
- Preserve existing v1 payloads for PracticalRecordConfirmed/Revised, AssessmentPassed/Failed and School enrollment lifecycle. Add `TrainingEvidenceInvalidated`, `AssessmentResultRevised`, `SchoolLearningAuthorityChanged`, and consumption of Scheduling `LessonParticipantsChanged`; see the implementation AsyncAPI export. New subscriptions must filter Subject/eventType. File publication, notifications and downstream redrive ownership remain with those service owners.
- Source/checklist/legal completeness is verified separately from external reporting. An evidence snapshot can be historically Ready yet not currently releasable. Unknown configured checks remain Unverified. A declaration records manual action and cannot represent transmission, import compatibility or Regitra acknowledgement.

Cross-service calls use bounded admission and fresh owner decisions, not a distributed transaction or instantaneous revocation guarantee. Already published documents and School status history remain historical evidence; later defects create holds/review rather than silent deletion. No production policies, credentials, public ingress or deployed CI/broker are implied by local tests.
